# UI_ALPHABET — единый контракт интерфейса платформы

**Нормативный источник для User, Professional и Администратора.** Владелец документа — `co-va/core`. Этот файл существует в одном месте: `co-va/core/staging/UI_ALPHABET.md`. Его не копируют в другие репозитории. Версия протокола: `UI-CONTRACT-1`.

## 1. Порядок чтения в новом чате

1. Прочитать `PROJECT_STATE.md` своего репозитория и этот `UI_ALPHABET.md` **из текущей ветки staging Core**, не из памяти предыдущего чата.
2. Прочитать `co-va/core/staging/BUSINESS_ARCHITECTURE.md` для F/E/режимов/capabilities и границ данных.
3. Для Professional прочитать `co-va/professional/staging/RELEASE_CLOSURE_MAP.md` и **живой** `RELEASE_CLOSURE_REGISTRY.json`; это действующий реестр технической приёмки, не вторая карта UI. Для User и Admin прочитать свои `PROJECT_STATE.md` и существующие тесты; статус Professional нельзя переносить на другие приложения.
4. Перед правкой общего UI прочитать действующий эталон в `co-va/user/staging` (`AGENTS.md`, `CI_CONTRACT.md`, `PROJECT_STATE.md`, исходники и CI), проверить текущие реализации во **всех затронутых репозиториях**, API-контракт в Core и SHA веток. Если источник недоступен — не утверждать, что проверено.
5. Работать в `staging` только своего разрешённого репозитория. Нельзя менять другой репозиторий, `main`, эталон, тесты или контракт по собственной инициативе. Обнаруженную межрепозиторную зависимость явно зафиксировать и согласовать с ответственным исполнителем.

## 2. Собственность

- `co-va/core`: API/БД, серверные правила доступа, бизнес-архитектура, платформа, Администратор, тарифы, **этот единый UI-контракт**. Core не владеет клиентским frontend User/Professional.
- `co-va/user`: интерфейс User. **Действующий эталон общих UI-примитивов — `co-va/user/staging`**, начиная с проверенного commit `78b28db45a6d84082978055f0789f98f08054533` (13.11.2026) и последующих явно проверенных изменений. `user/main` — историческая точка сравнения, не эталон для этих примитивов. Эталон реализации не означает автоматической визуальной приёмки всех экранов на устройстве.
- `co-va/professional`: интерфейс Professional, Журнал, рабочие операции. `professional/staging` сейчас развивается, не считать его автоматически UI-эталоном.
- Администратор использует доступные общие примитивы из Core `ui/**`. На телефоне — семейство мобильных компонентов, на компьютере — существующая адаптивная оболочка `admin/**`; это разные компоновки **одной системы**, а не разрешение на новый UI-набор.

**Критерий синхронизации:** каждый исполнитель переносит **семантику и точный размер**, а не весь файл с чужой бизнес-логикой. Отклонения фиксируются до исправления; экранные CSS-костыли не допускаются. Для Admin desktop сохраняется собственная сетка навигации и таблиц: мобильный контракт Z/Q не разрешает переписывать десктоп с нуля. Проверять computed CSS/DOM, реальный сценарий, клавиатуру и геометрию на устройстве; CI не заменяет приёмку владельцем.

**Статус:** геометрия эталона подтверждена владельцем и CI в User, но визуальная приёмка всех потребителей в Professional/Admin не следует автоматически. В каждой реализации отдельно сохранять commit SHA, проверку и факт приёмки; не маркировать весь продукт как `locked` без доказательств.

## 4. Что означает «утверждено»

Нельзя одним статусом смешивать:
- **Визуально принято владельцем:** внешний вид на конкретном экране/состоянии подтверждён. Отмечать только конкретный эталон и версию (commit SHA / снимок).
- **Функционально проверено:** реальные действия, API, данные, ошибки и повторный вход проверены на согласованных сборках.
- **Технически защищено:** проверки обнаруживают изменения общего компонента **и локальные CSS-переопределения у его потребителей**; защита ветки подтверждена GitHub.

Пока доказательства не сохранены, **не** заявлять `locked`/«всё готово». Положительная оценка User владельцем — исходное дизайнерское требование, а не разрешение объявить все сценарии прошедшими тесты.

## 5. Запреты на регрессии

- Не менять ни один уже принятый размер, цвет, отступ, поведение, форму или вариант компонента без **отдельного разрешения владельца**. Нельзя исправлять одну страницу глобальным переопределением другой.
- Не создавать вторую кнопку, модальный механизм, мини-карту, календарь или новую палитру вместо исправления единственного владельца.
- Нельзя считать одинаковым UI только потому, что файлы называются одинаково. Не переносить бизнес-логику из Core в User/Professional.
- До правки: определить ID, исходник и потребителей; после: адресные визуальные/функциональные проверки затронутых поверхностей и документированное основание. Нельзя ослаблять проверку ради зелёного CI.
- Присутствие этого документа **не** включает автоматическую защиту GitHub и не доказывает визуальную идентичность. Такие гарантии реализуются и подтверждаются отдельно; пока их нет, статус «защищено» запрещён.
