# UI_ALPHABET

Это единственный словарь визуальных, интерактивных и навигационных сущностей приложения.
Если нужная сущность уже существует здесь, новая реализация запрещена.
Контракт одинаков для профессионального интерфейса и интерфейса конечного пользователя: содержимое и сценарии могут различаться, владельцы букв и правила их поведения — нет.

## H / Header A-B-C-D

- H всегда является общим чёрным системным фоном. Для H нельзя создавать отдельную реализацию по роли пользователя или инструменту.
- В состоянии меню H показывает: A — фото текущего субъекта без действия, B — `Меню`, C — отсутствует, D — вход в Messenger. F/E/Z продолжают работать по своему Shared-контракту.
- Под «фото» понимается визуальный знак текущего субъекта: в профессиональном интерфейсе это фото профессионального профиля, в соответствующем контексте конечного пользователя — его фото. Отдельной сущности «логотип вместо фото» нет.
- A показывает фото текущего контекста. Если у текущего субъекта/объекта существуют внутренние настройки, A обязан показывать Shared settings-tag (шестерёнку). Локальная кнопка настроек рядом с A запрещена.
- B показывает только присвоенный текущему контексту заголовок. Если заголовок не присвоен, B пустой. Feature-код не придумывает fallback-заголовок. Единственное системное значение H — `Меню`.
- C существует только когда прямо сейчас существует реальное контекстное действие. Если действия нет, C полностью отсутствует и не занимает визуальное место.
- Если действие существует сразу при открытии экрана, C присутствует сразу. Если действие возникает только после изменения данных, например `Сохранить`, C появляется только после фактического изменения и исчезает после отмены/сохранения, когда действия снова нет.
- Disabled/пустой C как визуальный placeholder запрещён. Состояние «действия нет» выражается отсутствием C.
- В APP-состоянии D с иконкой чата всегда означает `включить Messenger`. Feature-код не выбирает иной маршрут D и не открывает локальный чат.
- В корне Messenger Z1 D меняется на явный control `вернуться в приложение`; это единственный способ выключить Messenger.
- В Messenger Z2+ D принадлежит текущему Messenger-контексту. Для обычного диалога D — скрепка/вложения. Из диалога нельзя одним D выйти в APP.
- Профессиональный и конечный пользователь используют один Messenger shell и один набор правил D/Z. Различается только доступный функционал.
- Реестр будущих режимов `Профессионал / Потребитель / Messenger / Соцсеть` может существовать как архитектурный резерв, но текущий D не обязан показывать общий picker режимов и не усложняется cross-domain auth до отдельной реализации.
- Feature-код не передаёт токены авторизации через URL между доменами.

## Messenger Mode

- `core/chat/messenger-mode.js` — единственный runtime-владелец режима Messenger для профессионального и конечного пользовательского интерфейса.
- APP и Messenger — два разных рабочих состояния одной оболочки. Включение Messenger не уничтожает и не перерисовывает APP-состояние под ним.
- При входе в Messenger точный APP-контекст сохраняется фактически самим нижним живым стеком: F/E/Z, выбранный объект и текущая глубина остаются под Messenger.
- Messenger Z1 всегда накладывается поверх любого текущего APP Z как отдельный независимый Z-стек.
- Messenger Z1 не dismissible: на нём нет свайпа вправо, нет кликабельного swipe/dismiss affordance и нет холостого индикатора шага назад.
- Выход из Messenger возможен только D из Messenger Z1. При выходе снимается Messenger-стек и снова проявляется ровно тот APP-контекст, который оставался под ним.
- Messenger Z2/Z3… — обычные рабочие слои внутри Messenger. Они снимаются по одному вправо и имеют Shared affordance, потому что у них существует реальный предыдущий Messenger-шаг.
- Обычный диалог — Messenger Z2. Его D — вложения. Сначала Z2→Z1, только затем D из Z1 может выключить Messenger.
- `Z Header` Messenger использует ту же Shared-геометрию, что остальное приложение; `Z Body` — единственная прокручиваемая рабочая область. Локальный header, отдельная геометрия Z и локальная swipe physics запрещены.
- На текущем этапе ядро Messenger содержит только собственный внутренний канал `CHAT`.
- `PUSH` не является пользовательским каналом Messenger. Push — технический механизм уведомления устройства. Пока серверная совместимость ещё использует `PUSH/IN_APP`, это преобразование обязано быть скрыто только за `core/chat/internal-chat.js` и не должно просачиваться в Messenger UI/core.
- Telegram, Email, MAX, WhatsApp, SMS и другие внешние каналы не определяют архитектуру Messenger и не импортируются в Messenger core до завершения собственного внутреннего мессенджера.
- Существующие внешние интеграции не удаляются: позже они подключаются как adapters к готовому Messenger, не меняя его shell, навигацию и внутреннюю модель.

## Calendar

- `ui/calendar` — единственный владелец `Calendar`, `DatePicker`, `DateNavigator` и геометрии навигации по дню / месяцу / году.
- Одна и та же Shared-навигация `← label →` используется независимо от данных: день, месяц, дата рождения, дата операции, дата записи и любой другой календарный контекст.
- Размер, border, radius, gap, typography и расположение стрелок задаются только `ui/calendar/calendar.css`; feature-код не имеет права переопределять их CSS, inline-style или modifier-классом.
- Feature-код может передать дату, режим, ограничения, callbacks и перенести уже готовый Shared calendar header в свой `Z Header`, но не имеет права менять его классы или визуальную геометрию.
- Локальные варианты вроде `compact`, feature-specific calendar navigation и собственные стрелки периода запрещены. Изменение Shared Calendar должно автоматически проявляться у всех его потребителей.
- Каноническая геометрия навигации Calendar: стрелки `36×36`, glyph `18`, border `1`, radius `8`, gap `4`; label `14/700`.

## Z Header / Z Body

- Z — главная рабочая поверхность. Каждый Z1/Z2/Z3… всегда состоит из двух Shared-частей: `Z Header` и `Z Body`.
- Уровень Z всегда определён явно. Z2/Z3… накладываются поверх предыдущего уровня и снимаются по одному; замена/перерисовка предыдущего уровня вместо стека запрещена.
- `Z Header` существует всегда как геометрическая зона, даже когда в нём нет пользовательского заголовка, поиска, переключателя или другого control.
- Минимальная высота `Z Header` — `40 px`. Она может увеличиваться только из-за реального содержимого Header.
- В левой зоне dismissible Z живёт один Shared swipe/dismiss affordance. Он обозначает реальную возможность снять текущий слой вправо, кликабелен как альтернатива свайпу, не содержит слова `Назад` и имеет читаемую тень/контраст.
- Если реального шага назад нет, affordance не существует. Канонический пример — Messenger Z1.
- Tap по левому affordance выполняет ровно тот же переход и ту же механику снятия слоя вправо, что успешный swipe: Z3→Z2, Z2→Z1; для обычного APP Z1 дальнейшую навигацию определяет текущий Shared navigation owner.
- Информационный control `I`, если он существует в текущем Z, всегда находится в правой зоне `Z Header`. Левое размещение `I` запрещено: левая зона зарезервирована за swipe/dismiss affordance там, где affordance существует.
- После содержимого `Z Header` всегда остаётся финальный визуальный gap до начала `Z Body`.
- `Z Body` содержит рабочее содержимое экрана. Запись feature-кода в корневой контейнер Z с уничтожением `Z Header` запрещена: обновляется только Shared `Z Body` либо монтируется новый Shared Z-слой.
- До отдельной миграции конкретного экрана всё текущее содержимое инструмента сначала принадлежит `Z Body`. Автоматически угадывать и переносить существующие controls в `Z Header` запрещено.
- В `Z Body` могут последовательно сочетаться проявления content / full / list. Это не разные типы Z, а разные проявления одной рабочей поверхности.
- Между соседними проявлениями `Z Body` обязателен визуальный gap, чтобы содержимое не сливалось.
- Проявление list, если присутствует, является терминальным: после list в `Z Body` нельзя размещать content или full.
- `Z Header` не является глобальным Header A/B/C/D и не принадлежит зоне H. Эти владельцы и геометрии независимы и не могут подменять друг друга.

## Жесты

- F: native horizontal scroll.
- E: native vertical scroll.
- E → вправо: закрыть E.
- Обычный APP Z1: переход к меню только через текущего Shared navigation owner.
- Messenger Z1: swipe вправо отключён; шага назад нет; выход только через D.
- Messenger Z2/Z3+: Shared swipe/affordance снимает только один верхний Messenger-слой.
- Остальные Z2/Z3: Shared swipe/affordance закрывает только один верхний слой.
- Tap по Shared Z affordance выполняет тот же один шаг возврата, что и успешный swipe вправо. Отдельная tap-навигация запрещена.
- `Z Header` остаётся на месте при вертикальном scroll Z; `Z Body` движется независимо от него.
- Верхние sticky-элементы конкретного инструмента в будущем переносятся в `Z Header` только после ручной классификации эталонного экрана; feature-код не создаёт собственную параллельную верхнюю зону.
- Верхняя зона affordance не принадлежит edge-swipe host, чтобы tap по affordance не спорил с распознаванием свайпа; ниже неё left-edge swipe остаётся прежним.
- Z-content: native scroll без локального перехвата.
- HorizontalRail владеет своим горизонтальным scroll и не двигает Z.
- Один pointer gesture имеет только одного владельца.
- Нижний Z под открытым Z2/Z3 всегда inert и pointer-dead.
- Частично отведённый Z не делает F интерактивным.
- Открытый Q/X/S блокирует FEZ до полного закрытия modal; исключения Header C/D для Q определены ниже.
- Feature-код не создаёт `pointerdown/pointermove/touch*`, `touch-action`, drag physics или screen-edge logic.

## Modal

- Feature-код вызывает только Shared modal API.
- Локальная modal geometry, backdrop, fixed-layer и собственное направление появления запрещены.
- Q/X/S не подменяются Z2/Z3 и наоборот.
- Нижний рабочий modal всегда X, верхний информационный всегда S, большой рабочий modal всегда Q.
- Q использует тот же Shared `Header + Body` и тот же принцип слоёв, что Z. Если открываются Q2/Q3/Q4…, верхний Q снимается по одному свайпом/левым affordance, возвращая предыдущий Q без перерисовки.
- В Q левая зона Header принадлежит swipe/dismiss affordance, `I` при наличии всегда справа.
- Для Q не вводится отдельное обязательное правило A: наличие/отсутствие A определяется реальным контекстом через общий Header owner.
- При открытом Q Header C и D остаются интерактивными. Вуаль Q не имеет права перехватывать их нажатие. A/B и FEZ под Q остаются недоступны как действия нижнего слоя.
- Нажатие на backdrop/вуаль или разрешённую область приложения вне тела активного modal закрывает только верхний modal и не передаёт исходное нажатие лежащим ниже слоям. Для Q C/D являются исключением и получают своё нажатие вместо veil-dismiss.
- S — только информационное/техническое сообщение. В S запрещены `Применить`, `Сохранить`, подтверждение и любые другие action-кнопки/рабочие controls. S закрывается Shared свайпом или tap-dismiss.
- X — рабочий нижний modal. В нём допустимы action/editor/picker и их кнопки согласно роли X.
- Поведение X определяется не фактом `X`, а его семантической ролью Shared modal: `action`, `editor`, `picker`.
- `X-action` — быстрый modal с кнопками действий. Когда выбранное действие открывает следующий X, `X-action` передаёт управление и закрывается; он не остаётся нижним слоем.
- `X-editor` — modal редактирования данных/формы. Открытый из его тела `X-picker` или другой дочерний выбор не закрывает `X-editor`; после закрытия дочернего X пользователь возвращается в тот же редактор с черновым выбранным значением.
- `X-picker` — выбор значения (например TimePicker/Selector). Он закрывает только себя и возвращает выбранное значение живому родительскому `X-editor`.
- `X-editor` сохраняет данные только по явному действию `Сохранить`/подтверждению, предусмотренному редактором. Swipe, tap по backdrop/вуали или другое обычное закрытие `X-editor` не является сохранением: несохранённый черновик отбрасывается, исходные данные остаются без изменений.
- Запрещено глобальное правило `если X уже открыт — второй X запрещён/заменяет первый`. Решение о handoff или stack принимает только Shared modal owner по семантической роли X.
- Разные application-modal Q/X/S могут открываться слоями, когда по контракту родитель должен оставаться живым; `X-action → X` является handoff, `X-editor → X-picker` является stack.
- Повторное открытие того же modal с той же идентичностью запрещено: одинаковый Q/X/S не дублируется в стеке.
- Пока существует стек Q/X/S, пользователь взаимодействует только с верхним активным modal и разрешёнными Header controls текущего modal-контекста.
- Полоса свайпа X/S занимает отдельное место в отступе Shared modal и не перекрывает содержимое.
- Каноническая проверка X-контракта — `scripts/check-modal-browser-interaction.mjs`: `X-action → X-editor → X-picker`, возврат picker в живой editor, отмена editor без сохранения, сохранение только кнопкой, Selector и реальный `openDayWorkplaceTime()` в Chromium desktop/mobile и WebKit mobile.

## Selector

- `ui/selectors` — единственный владелец Selector/SearchableSelector и их геометрии.
- Текущее выбранное значение в закрытом select всегда визуально центрировано независимо от feature и переданных данных.
- Список значений в открытом X-picker также центрирует данные. Feature-код не переводит значения selector вправо/влево собственными классами или CSS.
- Chevron/служебный indicator может занимать свою служебную область и не смещает визуальный центр данных.

## CSS

- Feature CSS не создаёт копии Shared UI.
- Feature CSS может раскладывать только собственный контент.
- Геометрия Header/F/E/Z/modal/cards/lists/calendar/time/receipt/document меняется только у Shared owner.
- Мёртвый и неподключённый CSS запрещён.
- Удалённый CSS не может оставаться подключённым из HTML.

## Runtime

- Мёртвый JS запрещён: каждый runtime-модуль должен быть достижим от реального application entry.
- Transition bridge / legacy / compatibility runtime запрещены.
- Старые readiness flags/tables запрещены.
- Новый инструмент не получает отдельный storage/UI/gesture owner, если такой owner уже существует.
- Профессиональный интерфейс и интерфейс конечного пользователя не создают параллельных реализаций H/A/B/C/D/Z/Q/X/S/Selector. Они передают разные данные одному Shared owner.

## Новая сущность

Новый UI-примитив допускается только когда:
1. существующего примитива действительно нет;
2. он зарегистрирован здесь;
3. назначен один Shared owner;
4. добавлен guard/test;
5. только после этого его использует функциональный инструмент.
